# swa：为什么连排序都救不了它

`prefill_attn_swa` 是 percounter 相对 legacy 落后最多的模块（−16.86%），也是
DeepSeek-V4.1-Flash 的 prefill 注意力里权重第三大的模块——只有 2 层，却占 22.6%
的时间，因为单层比 `prefill_attn_c2a_reuse` 贵 7.3 倍。把已验证的顺序修法全部代入
之后，它占剩余缺口的 **61%**。

另一个模块 `prefill_attn_c2a_reuse` 的同类缺口被**一次同层交换**从 −12.96% 修到
−1.50%（见[顺序表问题](order-list-problem.md)）。同样的手段在 swa 上只值 2.08%。
这篇讲清楚为什么。

**结论先说**：swa 的缺口不在顺序上，也不在任务交接上。它在**一个任务能同时用到
多少条 lane** 上，而那个数由任务自己的宽度和一个常数决定，**与它在顺序表里的位置
无关**。顺序是一维的排列，缺陷在二维的分发上。

## 一、这张图是什么

95 个任务，68 个在关键链上。b-level 从 70 单调降到 0，**每降一级就是一个任务**——
也就是说它基本是一条**链**，不是一张有宽度的 DAG。

```text
2 → 4 → 6 → 7 → 8 → ... → 14 → 16 → 17 → 18 → 19 → 21 → ... → 93 → 94
```

全图 95 个任务里，**只有 4 对处在同一个 b-level**（31/32、57/58、77/78、87/88）。
其余每个任务都严格排在它的前驱之后。

任务本身是宽的，宽度跨三个数量级：

| 每任务块数 | 任务数 | 典型每块耗时 |
| ---------- | -----: | ------------ |
| 1 | 7 | 2 µs |
| 4 | 9 | 119 µs（MIX） |
| 10 | 9 | 830 µs（MIX） |
| 40 | 9 | 450 µs（MIX） |
| 64 | 22 | 17~189 µs |
| 256 | 9 | 100~135 µs（MIX） |
| 512 | 4 | 27~87 µs |

机器有 32 条 AIC lane、64 条 AIV lane。

**所以这张图的形状是：一条很长的链，链上每一环自己很宽。** 环与环之间没有并行，
环内部有大量并行。这和 `c2a_reuse` 不同——后者同一 b-level 上有真正并列的任务，
所以"谁先谁后"是个真问题。

## 二、慢在哪里：不是交接

既然是链，第一个要怀疑的是**交接延迟**：前一个任务的最后一块结束，到后一个任务的
第一块开始，中间隔多久。链有 68 环，每环多付 40 µs 就是 2.7 ms。

量过了，**方向相反**。对每条依赖边算 `后继首块开始 − 最晚前驱末块结束`：

| 调度器 | 交接间隙合计 |
| ------ | -----------: |
| percounter | 298 µs |
| legacy | 460 µs |

（73 条依赖边合计。）

关键链上逐环看，percounter 的交接几乎全是 **2~7 µs**，legacy 是 **3~10 µs**。
percounter 每一环都更快——这正是它的设计目的：lane 直接轮询生产者计数器，不经过
AICPU 派发。**交接不是问题，而且是 percounter 赢的地方。**

## 三、慢在哪里：任务自己变长了

把每个任务的**跨度**（末块结束 − 首块开始）两边对比，按块数分档：

| 每任务块数 | 任务数 | percounter | legacy | 差值 |
| ---------- | -----: | ---------: | -----: | ---: |
| 1~9 | 16 | 1.11 ms | 1.10 ms | +1.7% |
| 10~63 | 24 | 7.96 ms | 7.55 ms | +5.5% |
| **64** | **22** | **8.90 ms** | **2.60 ms** | **+242.8%** |
| 65 以上 | 13 | 6.69 ms | 7.93 ms | **−15.6%** |

**所有的亏都在"块数恰好等于 64"这一档，而 64 正是 AIV lane 的条数。**

比它窄的档持平，比它宽的档 percounter 反而**快 15.6%**。

关键链上五个任务贡献了绝大部分：

| 任务 | 块数 | 每块耗时 | percounter 跨度 | legacy 跨度 | 倍数 |
| ---: | ---: | -------: | --------------: | ----------: | ---: |
| 57 | 64 | 185 µs | 668 µs | 218 µs | 3.1× |
| 31 | 64 | 189 µs | 652 µs | 232 µs | 2.8× |
| 35 | 64 | 172 µs | 594 µs | 205 µs | 2.9× |
| 61 | 64 | 173 µs | 441 µs | 209 µs | 2.1× |
| 78 | 64 | 18 µs | 939 µs | 51 µs | 18.4× |

同时它在宽任务上**退钱**：

| 任务 | 块数 | percounter 跨度 | legacy 跨度 |
| ---: | ---: | --------------: | ----------: |
| 39 | 512 | 103 µs | 566 µs |
| 65 | 512 | 104 µs | 459 µs |

关键链上净多付 **+1.40 ms**。

## 四、为什么偏偏是 64

percounter 的 lane 不是一块一块领工作的。它从票据里领一段**连续的顺序表位置**，
一次 `PERCOUNTER_CLAIM_BATCH = 4` 个，然后把这 4 个位置的块**依次**跑完。

于是一个占 N 个位置的任务，被切成 `N / 4` 段，**最多只有 `N / 4` 条 lane 同时在跑它**：

| 任务块数 | 切成几段 | 最多几条 lane | 相对 64 条 lane |
| -------: | -------: | ------------: | --------------- |
| 64 | 16 | 16 | **只用到 1/4** |
| 256 | 64 | 64 | 刚好用满 |
| 512 | 128 | 64（每条 2 段） | 用满，且票据开销摊薄 |

实测的"串行深度"（跨度 ÷ 每块耗时）对上了：任务 31/35/57 分别是 **3.45 / 3.46 /
3.61**，而 legacy 是 **1.23 / 1.19 / 1.18**。legacy 把 64 块发给 64 个核，一核一块；
percounter 把 64 块发给 16 条 lane，一条四块。

**这就是全部机制。** 它只在 `块数 ≈ lane 数` 时有害：

- 块数远大于 lane 数（256、512）：反正每条 lane 都要跑好几块，分段不损失并行，
  而且少领几次票据反而**赚**——这就是 39 和 65 快 5 倍的原因。
- 块数远小于 lane 数（1、4、10）：本来也用不满，无所谓。
- 块数恰好等于 lane 数：**唯一一个"本可以一块一条 lane"的点，被 4 的粒度砍掉 3/4。**

## 五、为什么顺序救不了

### 1. 这张图几乎没有顺序自由度

顺序表必须是拓扑序。swa 是一条链，链上的顺序是**被依赖强制的**。全图 95 个任务里
只有 4 对同层——也就是说可以自由交换的位置只有 4 处。

### 2. 那 4 处都试过了

扫描器（`helpers/order_misfit.py`）在 swa 上给出的两个最高分候选是
`move 57 after 58` 和 `move 31 after 32`，分数比 `c2a_reuse` 那个值 10% 的赢家还高
3 倍。同时段 A/B 实测：**亏 0.5%**。

原因在数据里看得很清楚。任务 58 的跨度是 4.45 ms（legacy 只有 178 µs），看着像是
被 57 挡住了。但是：

- 58 的生产者在 9.42 ms 就绪，58 **9.43 ms 就开始了**——没有被挡住开始
- 58 在 **13.87 ms** 结束，57 在 **13.97 ms** 结束
- 它们的共同消费者 59 要等两个都完成，**绑定的是 57**

**58 那 4.45 ms 的拖沓是免费的**，因为 58 根本不在关键链上。把它提前不缩短任何东西。
这是扫描器的系统性失真：它用"被挡住的 lane 数 × 就绪时间差"打分，但不检查被挡住的
那个任务是否在关键链上。

### 3. 就算有神谕也只值 2.08%

不靠扫描，直接把 **legacy 实际跑出来的整条执行顺序**回放给 percounter
（`orderrank_patch.py`，逐边验证拓扑合法，66 个任务全部接受）：

| 配置 | device wall | 相对原样 | 相对 legacy |
| ---- | ----------: | -------: | ----------: |
| 原样 | 19,368,766 | — | −17.47% |
| legacy 执行序 | 18,965,416 | **+2.08%** | −15.02% |
| 单票据组 | 19,316,164 | +0.27% | −17.15% |
| 单组 + legacy 序 | 19,133,801 | +1.21% | −16.04% |

**+2.08% 是上界。** 它是"percounter 能表达的所有顺序里最好的那个"的一个强近似——
因为它就是最优调度器实际走的那条路。17 个点的缺口里，顺序只值 2 个点。

（顺带排除掉票据分组：改成单组只值 0.27%，**分组不是约束**。）

### 4. 根本原因：顺序和缺陷不在同一个维度上

这是最要紧的一句。

顺序表决定的是**什么时候轮到这个任务**。而 swa 亏在**这个任务轮到的时候能用几条
lane**，那个数是 `块数 ÷ 4`——**它只取决于任务自己的宽度和一个常数，与这个任务被
排在第几位毫无关系。**

把任务 57 挪到列表的任何一个合法位置，它仍然被切成 16 段，仍然只有 16 条 lane 能
同时跑它，跨度仍然是 legacy 的 3 倍。

> 顺序是一维的排列；缺陷在"位置如何分发给 lane"这一步，是二维的。
> 没有任何排列能改变一个一维对象在另一个维度上的投影。

`c2a_reuse` 的情况不一样：它真的有两个同层任务被排反了，一个早就绪的被一个晚就绪的
挡在后面，而且恰好有 64 条 lane 会被那次阻塞同时套住。那是**顺序问题**，所以顺序能修。
swa 没有这样的一对——它的顺序是被链强制的，强制出来的顺序本来就是对的。

## 六、改粒度试过了，两种都亏

既然机制是 `CLAIM_BATCH = 4`，最直接的想法是把它改小。都做过：

| 改法 | 结果 |
| ---- | ---- |
| `CLAIM_BATCH = 1` 全局 | prefill 两个模块各**亏** 5.82% / 3.70% |
| 按任务宽度限制一次抽取（`ceil(块数 / lane 数)`） | swa 从 −17.2% 变成 **−17.8%** |

原因是同一张顺序表里同时存在两种极端：

- 任务 57：64 块 × 185 µs —— **想要窄抽取**，这样 64 条 lane 各拿一块
- 任务 2、90、91、93、94：各 1 块 × 2 µs —— **想要宽抽取**，否则一次票据往返
  （一次 GM 原子操作）就比这块工作本身还贵

票据是一次服务一个抽取的。抽取变窄，抽取次数就成比例变多，票据本身变成瓶颈。
**swa 的链同时穿过这两种任务**，所以没有一个全局的 `CLAIM_BATCH` 能同时照顾到。

按任务宽度限额本来正是为了解决这个——对 64 块的任务算出的额度恰好是
`ceil(64 / 64) = 1`，正中目标。但它把那些任务压成逐个领取，省下的并行度被多出来的
票据往返吃掉，净值是负的。

## 七、这张图的下界：没有多少余量

| 下界 | 时间 |
| ---- | ---: |
| 关键链长（每任务只算一块的理论下界） | 16.93 ms |
| AIV 总工作量 ÷ 64 条 lane | 6.68 ms |
| AIC 总工作量 ÷ 32 条 lane | 9.74 ms |
| legacy 实测 | 16.49 ms |
| percounter 实测 | 19.27 ms |

**这张图是依赖受限的，不是吞吐受限的。** AIV 的全部工作摊到 64 条 lane 上只要
6.68 ms，而链本身就有 16 ms 以上——所以 **AIV 有六成时间空着是图本身决定的**，
不是调度器的锅。legacy 几乎贴着下界跑，percounter 高出约 17%。

这也解释了按 lane 的时间预算为什么会看到"93% 的时间在阻塞等待"：那个数字是真的，
但它**大部分是固有的**，不能当成可回收的余量来读。

## 八、留给看这篇的人

机制是清楚的，两个显而易见的修法都量过且都是负的。还没被排除的方向有三个，
按我们的判断排序：

1. **让一条 lane 能退回一个未就绪的位置。** 这是根因侧的修法，绕开"顺序对不对"。
   代价是认领要从"票据发连续区间"改成"按位置 CAS"，并重新论证无死锁——现有论证
   依赖"lane 阻塞在自己区间内最低的位置"这个性质（见 `percounter_claim_range`）。
   收益未评估。

2. **让抽取宽度随任务而变，但把票据开销也一起解决掉。** 第六节证明单改宽度不行，
   因为省下的并行被票据往返吃掉。如果抽取不再经过单一票据（例如每组多票据、
   或者按位置 CAS），宽度限额才可能变成净收益。这两条其实是同一件事的两面。

3. **接受它。** swa 只有 2 层。如果 1 和 2 的代价太大，把 prefill 注意力的 −9.03%
   作为已知短板记录下来也是一个选项——percounter 在 decode 侧是大幅领先的
   （+38.4% / +29.7% / +11.0%），合成用例领先 14%~94%。

**不建议再花时间在顺序上。** 第五节给出的是结构性的理由，不是一次实验的结果：
这张图的顺序被依赖强制，自由度只有 4 处，4 处全试过，神谕序只值 2.08%。

## 复现

```bash
# 顺序实验（四个配置，同时段）
python3 tools/percounter-perf/helpers/order_misfit.py <扫描波次目录>
# 注入一对同层交换
SIMPLER_EXP_ORDER_AFTER=57:58 ...
# 回放 legacy 的整条执行序
SIMPLER_EXP_ORDER_RANK=<任务 id 序列> ...
```

补丁在 `tools/percounter-perf/patches/`（`orderafter_patch.py`、`orderrank_patch.py`、
`tasktime3_patch.py`），**只打在实验副本上，不进产品代码**。

**本页数字的来源要分开读。** 第二、三、四、五节里逐任务的跨度和交接取自带
`tasktime3` 探针的插桩构建——探针本身会改变绝对耗时，所以那一组只用来读**结构**
（哪一档亏、亏在跨度还是交接）。第五节的顺序对比表和开头的 −16.86%
取自干净二进制的同时段波次，那一组才是**量级**的依据。
