# swa：为什么连排序都救不了它

`prefill_attn_swa` 是 percounter 相对 legacy 落后最多的模块（−16.86%），也是
DeepSeek-V4.1-Flash 的 prefill 注意力里权重第三大的模块——只有 2 层，却占 22.6%
的时间，因为单层比 `prefill_attn_c2a_reuse` 贵 7.3 倍。把已验证的顺序修法全部代入
之后，它占剩余缺口的 **61%**。

另一个模块 `prefill_attn_c2a_reuse` 的同类缺口被**一次同层交换**从 −12.96% 修到
−1.50%（见[顺序表问题](order-list-problem.md)）。同样的手段在 swa 上只值 2.08%。
这篇讲清楚为什么。

**结论先说**：swa 的缺口不在顺序上，不在任务交接上，不在领取粒度上，也不在任务
宽度上——五条路线都单独量过，五条都被否掉（第六节）。它在**一个任务就绪的那一刻
有几条 lane 是空闲的**上。而 lane 不空闲，是因为它们正握着别的、还没就绪的位置
自旋：percounter 的 lane 认领即绑定，不可退回。

顺序改不了这一点，因为顺序决定的是"什么时候轮到这个任务"，不是"那一刻谁有空"。

## 一、这张图是什么

95 个任务，68 个在关键链上。b-level 从 70 单调降到 0，**每降一级就是一个任务**——
也就是说它基本是一条**链**，不是一张有宽度的 DAG。

```text
2 → 4 → 6 → 7 → 8 → ... → 14 → 16 → 17 → 18 → 19 → 21 → ... → 93 → 94
```

全图 95 个任务里，**只有 4 对处在同一个 b-level**（31/32、57/58、77/78、87/88）。
其余每个任务都严格排在它的前驱之后。

任务本身是宽的，宽度跨三个数量级：

| 每任务块数 | 任务数 | 典型每块耗时 |
| ---------- | -----: | ------------ |
| 1 | 7 | 2 µs |
| 4 | 9 | 119 µs（MIX） |
| 10 | 9 | 830 µs（MIX） |
| 40 | 9 | 450 µs（MIX） |
| 64 | 22 | 17~189 µs |
| 256 | 9 | 100~135 µs（MIX） |
| 512 | 4 | 27~87 µs |

机器有 32 条 AIC lane、64 条 AIV lane。

**所以这张图的形状是：一条很长的链，链上每一环自己很宽。** 环与环之间没有并行，
环内部有大量并行。这和 `c2a_reuse` 不同——后者同一 b-level 上有真正并列的任务，
所以"谁先谁后"是个真问题。

## 二、慢在哪里：不是交接

既然是链，第一个要怀疑的是**交接延迟**：前一个任务的最后一块结束，到后一个任务的
第一块开始，中间隔多久。链有 68 环，每环多付 40 µs 就是 2.7 ms。

量过了，**不够大**。对每条依赖边算 `后继首块开始 − 最晚前驱末块结束`，percounter
侧 73 条边合计 **298 µs**，关键链上逐环几乎全是 **2~7 µs**。

percounter 的 makespan 是 19.3 ms，**交接总共占 1.5%**。17 个点的缺口不可能从这里来，
无论 legacy 的交接是多少。

> 同一份数据里 legacy 的交接合计是 460 µs，看上去 percounter 还更快。
> **这个对比不要引用。** `tasktime3` 探针每个任务写一次计数器，而 legacy 的
> AICPU 每次派发都要走一遍，代价正落在交接间隙里：同一个模块，探针让 legacy
> 慢 **14.7%**（16.41 → 18.83 ms），让 percounter 慢 **0%**（19.26 → 19.11 ms）。
> 所以本页所有"percounter 比 legacy 好"的逐项对比都被这个探针系统性地放大了，
> 只有 percounter 自己的绝对值是可信的。

## 三、慢在哪里：任务自己变长了

把每个任务的**跨度**（末块结束 − 首块开始）两边对比，按块数分档：

| 每任务块数 | 任务数 | percounter | legacy | 差值 |
| ---------- | -----: | ---------: | -----: | ---: |
| 1~9 | 16 | 1.11 ms | 1.10 ms | +1.7% |
| 10~63 | 24 | 7.96 ms | 7.55 ms | +5.5% |
| **64** | **22** | **8.90 ms** | **2.60 ms** | **+242.8%** |
| 65 以上 | 13 | 6.69 ms | 7.93 ms | **−15.6%** |

**所有的亏都在"块数恰好等于 64"这一档，而 64 正是 AIV lane 的条数。**

比它窄的档持平，比它宽的档 percounter 反而**快 15.6%**。

关键链上五个任务贡献了绝大部分：

| 任务 | 块数 | 每块耗时 | percounter 跨度 | legacy 跨度 | 倍数 |
| ---: | ---: | -------: | --------------: | ----------: | ---: |
| 57 | 64 | 185 µs | 668 µs | 218 µs | 3.1× |
| 31 | 64 | 189 µs | 652 µs | 232 µs | 2.8× |
| 35 | 64 | 172 µs | 594 µs | 205 µs | 2.9× |
| 61 | 64 | 173 µs | 441 µs | 209 µs | 2.1× |
| 78 | 64 | 18 µs | 939 µs | 51 µs | 18.4× |

同时它在宽任务上**退钱**：

| 任务 | 块数 | percounter 跨度 | legacy 跨度 |
| ---: | ---: | --------------: | ----------: |
| 39 | 512 | 103 µs | 566 µs |
| 65 | 512 | 104 µs | 459 µs |

关键链上净多付 **+1.40 ms**。

## 四、不是领取粒度

那一档的"串行深度"（跨度 ÷ 每块耗时）是实打实的：任务 31/35/57 分别是
**3.45 / 3.46 / 3.61**，legacy 是 **1.23 / 1.19 / 1.18**。legacy 把 64 块发给 64 个
核，一核一块；percounter 只让大约 18 条 lane 跑它，一条跑三四块。

最自然的解释是领取粒度：lane 从票据领的是一段**连续的顺序表位置**，一次
`PERCOUNTER_CLAIM_BATCH = 4` 个；那么 64 个位置切成 16 段，最多 16 条 lane。
数字对得上。

**但这个解释是错的，两条独立的证据都否掉它。**

**第一，批量本来就是动态的，而且在 swa 上多半已经取到 1。** 代码里两条规则：

```cpp
// 列表短于 64 个位置/lane 时，首次只领一个
cfg.first_batch = cfg.order_count <= PERCOUNTER_SHORT_LIST_PER_LANE * lanes ? 1 : PERCOUNTER_CLAIM_BATCH;
// 上一个 kernel 超过 3 µs，之后一次只领一个
batch = get_sys_cnt_aicore() - kernel_start >= PERCOUNTER_LONG_KERNEL_CYCLES ? 1 : PERCOUNTER_CLAIM_BATCH;
```

swa 的 AIV 列表约 2440 个位置、64 条 lane，`2440 ≤ 4096`，所以首次领 1；而它的块
是 17~190 µs，远在 3 µs 之上。上板直接数（`drawahead_patch.py`，`EXPD`）：

| 模块 | 结果 | 窄任务里领 >1 的比例 | 宽任务里领 >1 的比例 |
| ---- | ---: | -------------------: | -------------------: |
| decode_attn_swa | **+36.7%** | 100% | 91% |
| prefill_attn_swa | −17.4% | 50% | 64% |
| prefill_attn_c2a_reuse | −10.6% | 18% | 14% |
| lm_head | −61.8% | 10% | 无宽任务 |

（"窄"指块数不超过本核类型的 lane 数。）

**领得最宽的赢最多，领得最窄的输最惨——完全反相关。** 如果宽领取是病因，这张表
应该是反过来的。

**第二，把它强行压到 1，swa 纹丝不动。** 按任务宽度限制一次领取
（`drawwidth_patch.py`，对 64 块的任务算出的额度正好是 1）同时段实测：
swa 从 −17.35% 变成 **−17.68%**，动了 0.29%。

所以 18 条 lane 不是被粒度切出来的。**那 46 条 lane 是不在场**——任务就绪的那一刻，
它们正握着别的、还没就绪的位置自旋。这就是 percounter 的核心性质：
**认领即绑定，不可退回**。

这也解释了为什么宽任务反而赢：256、512 块的任务无论如何每条 lane 都要跑好几块，
"少几条 lane"在它们身上摊薄了，而少领几次票据是净赚——39 和 65 快 5 倍就是这么来的。

### 也不是任务宽度：把宽度拉开，percounter 纹丝不动

下一个自然的解释是"块数恰好等于 lane 数最敏感"——`B = L` 是唯一一个理想跨度为
一轮的宽度，少一条 lane 就直接成倍。**这条同样被实测否掉了。**

模型库里 prefill 侧所有的 worker 上限都写死在 64（`_PREFILL_WORKERS` 两处、
`WORKER_TILE` 一处，来源见[图的形状](prefill-vs-decode-graph-shape.md)）。把它改成
16 / 128 / 256，同一台机器、同一次会话、干净二进制：

| 上限 | legacy | percounter | 缺口 |
| ---: | -----: | ---------: | ---: |
| 16 | 17.976 ms | 23.241 ms | −22.65% |
| **64**（原样） | **16.313 ms** | 19.322 ms | −15.57% |
| 128 | 16.694 ms | 19.211 ms | −13.10% |
| 256 | 17.512 ms | **19.130 ms** | −8.46% |

缺口对宽度是**单调的，64 这一档上没有峰**。如果 `B = L` 是病因，64 应该是最差的
一档，往两边走都该好转。

分开看两列，才是这张表真正说的事：

- **legacy 在 64 上取到最小值**，往两边都变差——64 正好一块一个 AIV lane、一次填满、
  派发次数最少。这个常量对 AICPU 派发器是调好的。
- **percounter 在 64/128/256 上是一条平线**（19.32 / 19.21 / 19.13，彼此差不到 1%）。
  宽度翻四倍，它一点没变好。

**缺口收窄全是因为 legacy 变差，不是 percounter 变好。** percounter 在这张图上有一个
约 19.3 ms 的地板，宽度这个旋钮碰不到它。

（顺带：只把 64 改成 63 也没用，实测 −16.2% 对原样 −15.4%。63 块放在 64 条 lane 上
理想跨度照样是一轮，根本没离开所谓的敏感区——那一版是实验设计错了，不构成反证。）

一条对宽度免疫的平线反过来**支持**第五节的结论：如果 lane 是被钉在未就绪的位置上
自旋，代价只跟链和顺序表有关，跟任务多宽无关。

### 为什么 decode 不吃这个亏：同名，但不是同一张图

`decode_attn_swa` 和 `prefill_attn_swa` 是同一个 kernel 家族，差 36.7% 对 −17.4%。
用同一个探针量它们的图，差别一眼可见——**按块数加权**，不是按任务个数：

| 模块 | 总块数 | 窄于 lane 数 | **等于 lane 数** | 宽于 lane 数 | 最长链/任务 | 结果 |
| ---- | -----: | -----------: | ---------------: | -----------: | ----------: | ---: |
| decode_attn_swa | 5007 | 143 | **0** | 4864（97%） | 0.43 | **+36.7%** |
| decode_attn_c2a_reuse | 5295 | 175 | **0** | 5120（97%） | 0.44 | **+31.9%** |
| prefill_attn_c2a_reuse | 1585 | 177 | 256（16%） | 1152 | 0.49 | −10.6% |
| prefill_attn_swa | 6434 | 674 | **1408（22%）** | 4352 | 0.75 | −17.4% |

**两个 decode 模块在"等于 lane 数"这一档上是零块。** 一块都没有，而四个模块的好坏
正好按这一列排序：0% → 赢三十多个点，16% → 亏 10.6%，22% → 亏 17.4%。

**但这只是相关，不是因果**——上一小节的宽度扫描直接否掉了"宽度等于 lane 数"这条
解释。这一列可靠的读法是它背后的那件事：decode 把 97% 的块放进**两个 2048 块的
任务**里，让**调度器**去摊；prefill 把同样的活压成几十个 64 块的任务，每块内部再
串行跑一百多轮，摊法是**编译期写死的**。谁能摊、谁不能摊，才是两张图的分界。
逐任务的名字、块数来源和下标推导在[图的形状](prefill-vs-decode-graph-shape.md)。

`prefill_attn_c2a_reuse` 和 `decode_attn_c2a_reuse` 这一对最说明问题：**任务数只差
5 个**（37 对 32），结果差 **42 个点**。所以差别不在"图大不大"，在**工作怎么打包**。

> 同一个算子家族，prefill 和 decode 编出来的不是同一张图。
> decode 把工作单元一个一个交给调度器（2048 个 block，每个一个单元）；
> prefill 把它们打包成 64 个 block、每个 128 个单元，谁拿到谁跑完。

swa 还多吃一层：它的最长链占到任务数的 **0.75**，是一条链。
`prefill_attn_c2a_reuse` 只有 0.49，所以它被钉住的 lane 还有别的任务可填——
这就是为什么同样是 prefill，一次同层交换能把 c2a_reuse 救回来，而 swa 不行。

## 五、为什么顺序救不了

### 1. 这张图几乎没有顺序自由度

顺序表必须是拓扑序。swa 是一条链，链上的顺序是**被依赖强制的**。全图 95 个任务里
只有 4 对同层——也就是说可以自由交换的位置只有 4 处。

### 2. 那 4 处都试过了

扫描器（`helpers/order_misfit.py`）在 swa 上给出的两个最高分候选是
`move 57 after 58` 和 `move 31 after 32`，分数比 `c2a_reuse` 那个值 10% 的赢家还高
3 倍。同时段 A/B 实测：**亏 0.5%**。

原因在数据里看得很清楚。任务 58 的跨度是 4.45 ms（legacy 只有 178 µs），看着像是
被 57 挡住了。但是：

- 58 的生产者在 9.42 ms 就绪，58 **9.43 ms 就开始了**——没有被挡住开始
- 58 在 **13.87 ms** 结束，57 在 **13.97 ms** 结束
- 它们的共同消费者 59 要等两个都完成，**绑定的是 57**

**58 那 4.45 ms 的拖沓是免费的**，因为 58 根本不在关键链上。把它提前不缩短任何东西。
这是扫描器的系统性失真：它用"被挡住的 lane 数 × 就绪时间差"打分，但不检查被挡住的
那个任务是否在关键链上。

### 3. 就算有神谕也只值 2.08%

不靠扫描，直接把 **legacy 实际跑出来的整条执行顺序**回放给 percounter
（`orderrank_patch.py`，逐边验证拓扑合法，66 个任务全部接受）：

| 配置 | device wall | 相对原样 | 相对 legacy |
| ---- | ----------: | -------: | ----------: |
| 原样 | 19,368,766 | — | −17.47% |
| legacy 执行序 | 18,965,416 | **+2.08%** | −15.02% |
| 单票据组 | 19,316,164 | +0.27% | −17.15% |
| 单组 + legacy 序 | 19,133,801 | +1.21% | −16.04% |

**+2.08% 是上界。** 它是"percounter 能表达的所有顺序里最好的那个"的一个强近似——
因为它就是最优调度器实际走的那条路。17 个点的缺口里，顺序只值 2 个点。

（顺带排除掉票据分组：改成单组只值 0.27%，**分组不是约束**。）

### 4. 根本原因：顺序和缺陷不在同一个维度上

这是最要紧的一句。

顺序表决定的是**什么时候轮到这个任务**。而 swa 亏在**这个任务轮到的那一刻有几条
lane 是空闲的**——那是一个关于其余 63 条 lane 此刻在做什么的问题，顺序表里没有
这个信息，也不可能有：顺序是 bind 时写死的，而"谁此刻被哪个未就绪的位置卡住"
是运行时才成立的事实。

把任务 57 挪到列表的任何一个合法位置，到它就绪的那一刻，大部分 lane 仍然握在别处。

> 顺序是一个静态的排列；缺陷是一个运行时的状态。
> 没有任何静态排列能表达"此刻谁有空"。

`c2a_reuse` 的情况不一样：它真的有两个同层任务被排反了，一个早就绪的被一个晚就绪的
挡在后面，而且恰好有 64 条 lane 会被那次阻塞同时套住。那是**顺序问题**，所以顺序能修。
swa 没有这样的一对——它的顺序是被链强制的，强制出来的顺序本来就是对的。

## 六、五个旋钮，五次否定

swa 的缺口被五条独立的路线各试过一次，结果都是零：

| 旋钮 | 做法 | swa 上的结果 |
| ---- | ---- | -----------: |
| 顺序 | 回放 legacy 整条执行序（神谕上界） | +2.08% |
| 票据分组 | 8 组改成 1 组 | +0.27% |
| 领取粒度 | 按任务宽度限额，64 块的任务压到 1 | **−0.29%** |
| 任务宽度 | prefill 的 worker 上限 64 → 128 / 256 | +0.6% / +1.0% |
| sync_start | 5 个 64 块任务标成"等齐 lane 再一起跑" | **+0.2%** |

最后两条还顺带说明了方向：`sync_start` 那一版 percounter 动了 0.2%，而 **legacy
反而慢了 6.7%**（16.343 → 17.435 ms）——缺口从 −15.71% "收窄"到 −10.29%，全是
legacy 掉下来的。把六个图变体的 percounter 数放在一起看更清楚：

```text
w16 23.24 | w63 19.58 | w64 19.32 | 原样 19.39 | syncA 19.43 | w128 19.21 | w256 19.13
                       └────────────── 19.1 ~ 19.6 ──────────────┘
```

**除了把并行度砍到 16，没有任何图形状的旋钮能把 percounter 从 19.3 ms 挪开**，
而同样这些变体让 legacy 在 16.3~17.98 ms 之间动。
（`sync_start` 这一版只覆盖了 22 个 64 块任务里字面量宽度的 11 个，rope 那三个是
`min(·,64)`、没改，所以这是一次部分检验。）

对照：同样这几条在别的模块上**有**效果——`c2a_reuse` 一次同层交换值 +10.3%，
`c2a_full` 值 +3.8%，`lm_head` 的领取限额值 **+45 个点**。所以不是这些旋钮没用，
是 swa 不在它们能够到的那一类里。

领取限额在 `lm_head` 上为什么有效、在 swa 上为什么无效，对比很说明问题：

- `lm_head` 只有 9 个任务、92 个位置。一个 16 块的任务被几次宽领取发给 4 条 lane
  跑了 4 轮，而整张图没有别的工作能填进去——**一次宽领取就是全部损失**。
- swa 有 2440 个位置、68 环的链。它的 64 块任务拿不到 lane，不是因为 lane 把位置
  领走了，而是因为 lane **压根没空来领**。

并且领取限额在整体上是亏的：按 40 层骨干加权，它在 prefill 注意力上多花 2.78 ms、
在 `lm_head` 上省 0.90 ms，净 −1.88 ms，**已经回退**（见
[性能对比](perf-results.md)的"试过并回退"一节）。

## 七、这张图的下界：没有多少余量

| 口径 | 时间 |
| ---- | ---: |
| 关键链长（每任务只算一块，最松的下界） | 16.93 ms |
| 非 MIX 工作量 ÷ 64 条 lane | 1.81 ms |
| MIX 工作量 ÷ 64 | 9.84 ms |
| legacy 实测（插桩，偏大约 15%） | 18.83 ms |
| percounter 实测（插桩，偏差 < 1%） | 19.11 ms |

**这张图是依赖受限的，不是吞吐受限的。** 全部工作摊到整台机器上是个位数毫秒，
而链本身就有 16.9 ms——所以 **lane 大部分时间空着是图本身决定的**，不是调度器的锅。
这也解释了按 lane 的时间预算里"93% 的时间在阻塞等待"：那个数字是真的，但**大部分
是固有的**，不能当成可回收的余量来读。

**但"legacy 已经最优"这个结论本页给不出。** 16.93 ms 这个下界太松——它假设每个
任务只跑一块，而 512 块的任务在 64 条 lane 上至少要 8 轮。把轮数算进去得到
21.7 ms，**反而高于实测**，说明这个算法对 MIX 任务是错的：一个 MIX 块占一个
cluster 的一条 AIC 加一条 AIV，lane 数不是 64，而 `busy` 把两边都算了一遍。

所以目前只能说：**legacy 至少高于最松下界 11%**，上面还有多少空间没有量过。
要给出可信的 ideal，需要把 MIX 按 cluster 计数，并用干净二进制取每块耗时——
两者本页都没有。

## 八、留给看这篇的人

五条旋钮都量过，五条都是零。剩下的方向只有一个方向上的事：**让 lane 在就绪发生
的那一刻可支配**。按我们的判断排序：

1. **让一条 lane 能退回一个未就绪的位置。** 这是唯一直接针对第四、五节那个结论的
   修法：缺陷是运行时状态，所以修法也必须在运行时生效。代价是认领要从"票据发连续
   区间"改成"按位置 CAS"，并重新论证无死锁——现有论证依赖"lane 阻塞在自己区间内
   最低的位置"这个性质（见 `percounter_claim_range`）。收益未评估。

2. **让领取宽度随任务而变，但把票据开销也一起解决掉。** 第六节证明单改宽度在 swa
   上是零，但它在 `lm_head` 上值 45 个点，所以这条路不是死的，只是对 swa 无效。
   如果领取不再经过单一票据（例如每组多票据、
   或者按位置 CAS），宽度限额才可能变成净收益。这两条其实是同一件事的两面。

3. **接受它。** swa 只有 2 层。如果 1 和 2 的代价太大，把 prefill 注意力的 −9.03%
   作为已知短板记录下来也是一个选项——percounter 在 decode 侧是大幅领先的
   （+38.4% / +29.7% / +11.0%），合成用例领先 14%~94%。

**不建议再花时间在顺序上。** 第五节给出的是结构性的理由，不是一次实验的结果：
这张图的顺序被依赖强制，自由度只有 4 处，4 处全试过，神谕序只值 2.08%。

```python
# 宽度：三处常量，每个宽度跑 legacy / percounter 两个配置，同一次会话同一块卡

# sync_start：给字面量宽度的 spmd 加一个关键字

```

注意 percounter 对 `block_num < 2` 的 `sync_start` 任务会**拒绝整张图**，而
`SIMPLER_EXP_FORCE_SCHED=percounter` 遇到拒绝是直接报错返回（不会悄悄回落到
legacy），所以这类配置错误会表现为 `passed=False`，不会变成假的测量。

**只打在实验副本上，不进产品代码**。
