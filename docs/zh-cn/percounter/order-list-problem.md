# percounter 的顺序表排错了一对任务，代价是 10%

一个可以独立阅读的问题陈述。读完应该能回答：percounter 怎么调度、这个用例的依赖链
长什么样、问题出在哪一对任务、为什么现有的排序规则找不到它、以及还有哪些没查清。

实测结论先放前面：`prefill_attn_c2a_reuse` 这个模块上，percounter 比 AICPU 调度器
（下称 legacy）慢 12.06%；**把顺序表里相邻两个任务的次序对调一下，缺口变成 0.81%**。
这个对调是免费的——两个任务同属一个 b-level，彼此无依赖边，怎么排都合法。

## percounter 怎么调度

| 维度 | legacy | percounter |
| ---- | ------ | ---------- |
| 谁决定哪个核跑什么 | AICPU 集中派发 | 每条 lane 自己从一张**顺序表**上领位置 |
| 什么时候绑定 | 任务**已就绪**才派给空闲的核 | lane 用一次原子自增从票据上领一个位置，**不看就绪与否** |
| 领了之后能不能还 | 不存在"领" | **不能**。票据是单调计数器，没有退回路径 |

顺序表是主机侧在 bind 阶段生成的，每个核类型一张（AIC 一张、AIV 一张、MIX 一张）。
一个任务的 N 个块在表里占 N 个连续位置。lane 从票据上原子自增取位置，取到就对那个
位置负责到底：如果那个位置的任务还没就绪，lane 就在那儿等，**而且别的 lane 拿不走**。

percounter 的收益来自省掉集中派发——decode 的几个模块上快 11%~38%。代价就是这条
"认领即绑定、不可退回"。

顺序表现在按 **b-level 降序**排。b-level 是一个任务到图终点的最长路径，也就是"还有
多少活吊在它后面"。并列的按 task id（`stable_sort` 的副产物，没有调度含义）。

## 这个用例的依赖图

`prefill_attn_c2a_reuse`，DeepSeek-V4.1-Flash 的 prefill attention（C2A cache-reuse
变体），37 个任务。15 个是无依赖的单块源任务，真正的结构是两条分支汇合：

```text
分支 A（重）
  源 6 → 【投影】7  MIX, 10 块, 每块 453 µs
        → 8   AIV,   4 块
        → 【注意力】10  MIX, 256 块, 每块 27.9 µs
        → 11  AIV,  64 块  ────────────────────┐
                                               │
分支 B（长）                                    │ 汇合
  源 12 → 13  MIX,   4 块                      │
        → 15  AIV,   4 块, 每块 2.4 µs          │
        → 16  AIV,  32 块                      │
        → 17  AIV,  32 块                      │
        → 20  AIV, 256 块, 每块 5.5 µs          │
        → 21  AIV, 256 块, 每块 20.8 µs ────────┤
                                               │
  19  AIV, 32 块（生产者全是源，t=0 就绪）────────┤
                                               ▼
        22 MIX,128 → 24 AIV,64 → 27 MIX,128 → 28 AIV,128
        → 29 MIX,40 → 31 AIV,64 → 32 → 33 → 34 AIV,64 → 35 → 36
```

关键的几条边（`fanin` 是生产者列表，直接取自 `TaskPayload`，两种调度器读的是同一份）：

| 任务 | 核类型 | 块数 | 每块 | 生产者 |
| ---: | ------ | ---: | ---: | ------ |
| 7 | MIX | 10 | 453 µs | 6 |
| 10 | MIX | 256 | 27.9 µs | 3, 8, 9 |
| **11** | **AIV** | **64** | 43 µs | 4, 9, **10** |
| 19 | AIV | 32 | 1.4 µs | 2, 0（都是源） |
| 20 | AIV | 256 | 5.5 µs | 19, 0, 17 |
| **21** | **AIV** | **256** | 20.8 µs | 19, 0, **20** |

**MIX 任务的一个块要同时占用一个 cluster 的 AIC 和 AIV 两条 lane 协同执行**，所以
设备侧量到的"块数"是图里块数的两倍（`subtasks=2`）。

## 问题出在哪一对

主机侧 dump 出的真实 AIV 顺序表（位置 → 任务）：

| 位置 | 任务 | 块数 | 等谁 | 何时就绪 |
| ---: | ---: | ---: | ---- | -------: |
| 0–3 | 15 | 4 | 13 | 119 µs |
| 4 | 2 | 1 | — | 立即 |
| 5–36 | 16 | 32 | 15 | 477 µs |
| 37–40 | 8 | 4 | 7 | 473 µs |
| 41–72 | 17 | 32 | 16 | 483 µs |
| 73–104 | 19 | 32 | — | 立即 |
| 105–360 | 20 | 256 | 17 | 567 µs |
| **361–424** | **11** | **64** | **10** | **936 µs** |
| 425–680 | 21 | 256 | 20 | **750 µs** |

**64 个位置，而 AIV 正好有 64 条 lane。**

lane 跑完 20 的 256 个位置（结束 749,848）之后，接着领 361–424——**一条 lane 一个，
整池同时阻塞在 10 上，要等到 936,269**。而 21 的依赖在 749,848 已经满足，它的位置
排在 425 之后，**没有任何一条 lane 能够到**。

11 和 21 的 **b-level 都是 11**，并列，现在按 id 排所以 11 在前。

## 证据

按**块**（不是按任务）记录领取时刻、执行时刻、执行它的 lane，以及该 lane 在这两刻
的累计 kernel 数和累计忙时。任务 11 的 176 个采样：

| 量 | 值 |
| -- | -: |
| 领取到执行的握持 | 中位数 **377,098 ns**（最小 290,689，最大 531,373） |
| 其间的 kernel 忙时 | 中位数仅 **43,034 ns** |
| **空握**（握 >100 µs 却只干 <50 µs） | **170 / 176** |

64 条 lane 各空握约 334 µs ≈ **21 ms 的 lane 工时**，而整轮 AIV 池总容量约 151 ms
（2.36 ms × 64），**浪费 14%**。

**按任务看完全看不见这件事**：任务 11 的跨度只有 45 µs——它就绪之后跑得飞快。只有
按块的"领取 → 执行"才暴露出来。这是这个问题之前一直没被发现的原因。

## 已验证的修复

把 11 挪到 21 之后（同层无边，拓扑序不变）：

| 配置 | device wall | 相对 legacy |
| ---- | ----------: | ----------: |
| legacy | 2,261,495 | — |
| percounter 原样 | 2,534,247 | −12.06% |
| **percounter + 这一个交换** | **2,279,727** | **−0.81%** |

两次独立测量 +9.74% 和 +10.04%，正确性均通过。

## 为什么这条规则不好自动化

规则本身很好说：**同一 b-level 内，按这个任务实际能开始的时刻升序排。** 难在"实际
能开始的时刻"要估。两种不花代价的权重都挑不出这一对：

| 权重 | t(11) | t(21) | 谁在前 | 对不对 |
| ---- | ----: | ----: | ------ | ------ |
| 边数（距源最长路径） | 4 | 6 | 11 | 错 |
| 块数加权 | 271 | 329 | 11 | 错 |
| **实际时间** | **936 µs** | **750 µs** | **21** | **对** |

11 的生产者是 10（256 块、**每块 27.9 µs**），21 的生产者是 20（256 块、**每块
5.5 µs**）。**块数相同，耗时差 5 倍——边数和块数都看不见这个差别。**

按边数排的那一版实测只动了 0.29%：它确实改了顺序，但没改这一对。

## 为什么不能把 b-level 整个换掉

"按就绪时刻排"听上去比 b-level 更合理，但整套换掉实测**比原样慢 7.10%**，而且
损失全在 AIV 列表（只改 AIV −7.07%，只改 MIX +1.69%）。逐任务对比指出了唯一的
亏损源：

| 任务 | 相对原样 | 赚亏 |
| ---: | -------: | ---- |
| 21（向量，256 块） | −475,024 | 赚 |
| 15 | −337,369 | 赚 |
| 20 | −160,562 | 赚 |
| 19 | −84,390 | 赚 |
| **8（4 块）** | **+173,373** | **亏** |
| **10（【注意力】MIX，256 块）** | **+273,511** | **亏** |
| 22 之后全部 | +175,000 ~ +184,000 | 亏 |
| **makespan** | **+180,372** | |

**任务 10 的 `fanin` 是 `[3, 8, 9]`——它等任务 8。** 而任务 8 只有 4 个块，等
【投影】（结束 464,464）：

- **原样**：8 的位置在 37–40，4 条 lane 从 t=3 µs 就握着。【投影】一结束，8 在
  **466,412** 立刻开跑，只差 2 µs。
- **就绪序**：8 被挪到位置 614 附近，lane 要先啃完 20 和 21 的 512 个位置才够得到，
  于是 8 到 **627,622** 才开始——**就绪之后又等了 161 µs**。

8 晚 161 µs → 10 晚 273 µs → 整条尾巴晚 180 µs。

所以**握着一个未就绪的位置，其实是一个预置的扳机**：生产者一完成，这条 lane 立刻
就发。它的代价是一条 lane 空等，收益是下游一大片工作早启动，而这个比值完全取决于
那个任务后面吊着多少活——**那正是 b-level 的定义**。

| 情形 | 握着未就绪的位置 |
| ---- | ---------------- |
| 后面吊着大量工作（任务 8 → 【注意力】） | **好**，是预置扳机 |
| 后面吊着的不多，而身后排着已就绪的活（任务 11） | **坏**，白占 lane |

**结论：b-level 必须留作主键，可动的只有并列。** 任务 11 和 21 的 b-level 都是 11，
b-level 对它们没有意见，这时候按就绪时刻破并列才是对的——前面那个值 10% 的交换
正是这条规则的一个实例。

这把问题缩小了一大圈：**耗时估计只需要用来比较同层的任务**，不需要全局代价模型；
而且同层任务互不依赖，这种排序永远不会破坏拓扑序。

## 还没查清的两件事

**一、这个模式在别的模块里有几处？** 判据是机械的：同一条列表上，一个尚未就绪的
任务其位置数接近或超过该核类型的 lane 数，且它后面有已就绪的任务。`graphdump` 给
依赖和块数，`orderdump` 给真实位置，两者一对就能扫出来。还没对另外四个 prefill
模块做过。

**二、同层并列的就绪时刻怎么估？** 只需要能比较同层任务，不需要全局代价模型。
两条路：pypto 侧的静态估计（它知道 tile 形状和 dtype），
或者一次 profile 回灌。这决定了改动落在哪个仓。

## 旁边还有一个更小的问题

同一个模块里还有另一种停顿，形态完全不同，**值 1.4 ms lane 工时（比上面小 15 倍）**：
一条 lane 握着 AIV 位置的同时被拉进一个 453 µs 的 MIX rendezvous，位置被锁住。
三种修法都试过，一个无效、一个算错、一个崩溃，细节见
[percounter 为什么在 prefill attention 上慢于 legacy](prefill-attention-deficit.md)。
**它和本页讲的顺序问题是两件独立的事**，排序修不了它，它的修法也修不了排序。

## 怎么自己跑

```bash
python tools/percounter-perf/percounter_perf.py setup --name mine --source <干净 checkout>
python tools/percounter-perf/percounter_perf.py run   --name mine --out ~/runs/w1 \
       --cases deepseek --pypto-lib <pypto-lib checkout> --comm-pad64
python tools/percounter-perf/percounter_perf.py report --out ~/runs/w1
```

本页用到的探针都在 `tools/percounter-perf/patches/`，不参与 `setup`，要手动打：

| 补丁 | 日志前缀 | 给出什么 |
| ---- | -------- | -------- |
| `graphdump_patch.py` | `EXPG` | 每个任务的块数、MIX/sync、核类型、生产者。主机侧，不上板 |
| `orderdump_patch.py` | `EXPO` | 每条顺序表的实际排列，带 b-level 和 t-level。主机侧 |
| `blocktrace_patch.py` | `EXPB` | 指定任务**逐块**的领取时刻、执行时刻、lane，以及该 lane 在这两刻的累计 kernel 数和忙时 |
| `tasktime3_patch.py` | `EXPS` | 两种调度器各自的逐任务首尾时间戳 |
| `orderafter_patch.py` | — | `SIMPLER_EXP_ORDER_AFTER=A:B` 把 A 挪到 B 之后，**只允许同 b-level 的对** |
| `orderrank_patch.py` | — | `SIMPLER_EXP_ORDER_RANK=<ids>` 整体替换排序，**排完逐条边验证拓扑序**，不满足就回退并报错 |

用法和注意事项（特别是"换二进制必须等波次结束"、"要同步到三处加载位置"）见
[`tools/percounter-perf/README.md`](../../../tools/percounter-perf/README.md)。

**改行为的补丁一定要连 `passed=` 一起读。** 有一版看着快 13~20%，实际是 golden 不
匹配——它漏跑了活。只看时间会把"少干了活"读成"变快了"。
