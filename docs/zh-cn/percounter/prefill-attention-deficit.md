# percounter 为什么在 prefill attention 上慢于 legacy

讲一个已经定位到单个块的例子：DeepSeek-V4.1-Flash 的 prefill attention（C2A
cache-reuse 变体）在 a5 host_build_graph 上，percounter 比 legacy 慢 13%。

本页只讲这一个例子和它的成因。各模块的完整数字、以及一路上排除掉的十二个候选，
在[性能结果](perf-results.md)里。

## 一句话

**percounter 在一份工作"能跑"之前就把它绑定到某条 lane 上；而这条 lane 随后可能
被拉进一个 453 µs 的协同 kernel，在那期间它手里那份工作对其他所有 lane 都是不
可见的。** legacy 的 AICPU 只派发已就绪的任务，不存在这种绑定。

## 两种调度器的根本差别

| 维度 | legacy | percounter |
| ---- | ------ | ---------- |
| 谁决定哪个核跑什么 | AICPU 集中派发 | 每条 lane 自己从一张**顺序表**上领位置 |
| 什么时候绑定 | 任务**已就绪**才派给空闲的核 | lane 用一次原子自增从票据上领一个位置，**不看就绪与否** |
| 领了之后能不能还 | 不存在"领" | **不能**。票据是单调计数器，没有退回路径 |

percounter 的设计收益是省掉集中派发的开销。在 decode 的几个模块上这笔收益是
11%~38%。本页讲的是它的代价在什么形状的图上会显露出来。

## 这个例子的图

37 个任务，结构是两条分支汇合。下面用角色命名，这些角色是按实测的块数、核类型、
每块耗时和依赖关系认出来的，不是模型里的算子名。

```text
分支 A（重）  源 → 【投影】MIX, 10 块, 每块 453 µs
                  → 小向量(4 块) → 【注意力】MIX, 256 块 → 向量(64 块) ─┐
                                                                        │汇合
分支 B（长）  源 → 小 MIX(4 块)                                          │
                  → ★向量链第一环★ AIV, 4 块, 每块 2.4 µs                │
                  → 向量(32) → 向量(32) → 向量(256) → 向量(256) ────────┘
```

两个关键角色：

- **【投影】**：整张图最重的单体，也是一个 **MIX 任务**——它的一个块要同时占用一个
  cluster 的 AIC 和 AIV 两条 lane 协同执行。10 个块，每块 453 µs。
- **★向量链第一环★**：只有 4 个块、每块 2.4 µs，总共 9 µs 的活。但它是分支 B 那条
  长链的头，后面的 32→32→256→256 全在等它。

## 发生了什么

AIV 的顺序表按 **b-level 降序**排。b-level 是到图终点的最长路径，也就是"还有多少活
吊在这个任务后面"。分支 B 的链最长，所以 ★向量链第一环★ 的 b-level 在整个 AIV
列表里最高，**被排在第 0~3 号位置**。

| 时刻 | 发生的事 |
| ---: | -------- |
| ≈3 µs | 64 条 AIV lane 各领一个位置。头 4 个位置被 4 条 lane 领走。**该任务此时还没就绪**——它要等分支 B 的那个小 MIX 任务 |
| ≈10 µs | 这 4 条 lane 里有一条恰好是它所在 cluster 的 **MIX 认领者**。它为自己的 cluster 认领了【投影】的一个块，进入那个 453 µs 的 kernel |
| 119 µs | ★向量链第一环★ 就绪。另外 3 条 lane 立刻跑完自己那块，各 2.4 µs |
| 119→467 µs | **第 4 块卡住。** 持有它的 lane 在 kernel 里。其他 60 条空闲 lane 想帮也拿不到——位置已经被票据发出去了，没有退回机制 |
| 467 µs | 【投影】跑完，那条 lane 出来，花 2.4 µs 跑掉它那块 |
| 474 µs 起 | 分支 B 的 32→32→256 这才开始 |

同一模块在 legacy 下，这条链 13.7 µs 就开始推进，219 µs 已经到了 256 块那一级；
percounter 要到 594 µs。**差 375 µs，而整个模块只跑 2.4 ms。**

## 证据

按**块**（不是按任务）的设备时间戳，记录每块的领取时刻、执行时刻、执行它的 lane，
以及该 lane 在这两刻的累计 kernel 数和累计忙时
（`tools/percounter-perf/patches/blocktrace_patch.py`）：

| 块 | 领取→执行 | 其间跑了几个 kernel | 其间的 kernel 忙时 |
| -- | --------: | ------------------: | -----------------: |
| 迟到的那块 | 470 µs | 2 | 464,806 ns |
| 迟到的那块（另一轮） | 462 µs | 2 | 454,748 ns |
| 正常的块 | 123 µs | 1 | 2,430 ns |
| 正常的块 | 122 µs | 1 | 2,592 ns |

这组数排除了另外两种可能：

- **不是"票据没推进到那个位置"**——它在 3 µs 就被领走了。
- **不是"lane 在空等"**——它跑了两个 kernel、忙了 455~465 µs。减去自己那 2.4 µs，
  另一个是 ~453 µs，正是【投影】的一个块。

迟到的 lane 每次都是 `cluster_lane == 1`，也就是 MIX 认领者。

## 为什么 decode 不吃这个亏

decode 的骨干本来就是串行的，没有"一个长 MIX 任务和一串已就绪的独立向量任务同时
存在"这种并置——没有可抢的活，也就谈不上抢不到。同样的机制在 decode 上不产生代价，
而省下的派发开销实打实地留了下来。

## 一个值得注意的反讽

b-level 的本意是把最关键的任务排在最前。而最关键的任务往往是长链的头，**长链的头
恰恰是还要等前置才能开始的那个**。于是调度器把"最不能现在跑"的任务放到了 64 条
lane 开局必抢的位置上。

## 排序改不掉它

这张图里 t=0 就绪的 AIV 块只有 34 个（三个任务，其生产者全是源），而开局要占掉
64 个位置，所以**至少 30 条 lane 必须认领未就绪的位置**，与排序无关。

而拓扑序又锁死了未就绪那一段的内部顺序：`blevel(生产者) ≥ blevel(消费者) + 1` 是
严格的，所以那一段必须按 b-level 降序，★向量链第一环★ 的 b-level 最高，必然排在
最前，推不出前 64 名。

实测验证过：把同层并列的次序从 id 改成 t-level 升序，顺序表如期改变（开局可运行的
块从 1 个变成 28 个），九个模块的耗时整体中性偏负，`c2a_reuse` 只动了 0.29%。

## 两个候选修法

### A：lane 持有位置时不认领 MIX

当前形态（`patches/mixhold_patch.py`）无效，因为循环顺序是先认领 MIX、后领位置：

```cpp
percounter_mix_tick(cfg, &state);   // 认领 MIX
if (pending == 0) { ...领位置... }  // 领列表位置
```

第一次迭代时 `pending` 本就是 0，守卫恒为真。

把顺序调过来会引入**真死锁**：一条 lane 被未就绪的位置堵住就不认领 MIX，而那些
位置等的正是 MIX 的产出。这张图开局就有约 30 条 lane 落在未就绪位置上，其中约一半
是认领者；只要某张图让所有认领者都落在未就绪位置上，就是整机挂死。

### B：有未结清 MIX 认领时不领位置

当前形态（`patches/mixdraw_patch.py`）会让结果算错，但原因是守卫写宽了：

```cpp
if (pending == 0 && state.claim.task_id < 0 && state.claim.position < 0) {
```

`claim.position` 的语义是"抽到了一个 AICPU 还没发布的 MIX 条目"，可以长期挂着。
一挂住，这条 lane 就再也不领列表位置，它那份工作无人认领。表示"有未结清
rendezvous"的是 `task_id`，rendezvous 服务完就会清掉。

### 两者的对比

| 维度 | A（调序版） | B（窄版，只守 `task_id`） |
| ---- | ----------- | ------------------------- |
| 持有时长 | 可能**无界**——被未就绪位置堵多久就不认领多久 | **有界**——只在"已认领、未服务"之间，上限是一个 MIX kernel |
| 会不会连成环 | **会** | **不会**。被位置堵住的 lane `pending != 0`，本就不领新位置，而 B 不拦认领，MIX 照常推进 |
| 失败模式 | 挂死 | lane 在认领到服务之间空转，损失带宽——可测 |

**B 更有希望，且窄版尚未实测。** 它的代价是认领者在一次 rendezvous 期间不参与列表
工作，这段时长是可以量的；A 的失败模式是挂死，没法靠测量兜底。

### 两者之外

真正干净的解法是**让 lane 能退回一个未就绪的位置**。票据是单调计数器，没有退回
路径；要支持退回，位置的认领就得从"票据发区间"改成"按位置 CAS"，并重新论证无
死锁——现有论证靠"lane 阻塞在自己范围内最低的位置"成立，见
`percounter_claim_range`。这是设计改动，收益未评估。
